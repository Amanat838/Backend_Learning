## 9.1 Discriminated unions: variants with a tag

Sometimes a value can be one of several **shapes**, and each shape has different fields. Give every shape a shared **tag** field with a literal value, and TypeScript can tell them apart:

```ts
type Payment =
  | { method: "cash" }
  | { method: "card"; last4: string }
  | { method: "wallet"; provider: "JazzCash" | "Easypaisa"; phone: string };

function describePayment(p: Payment): string {
  switch (p.method) {
    case "cash":
      return "Pay at the counter";
    case "card":
      return `Card ending in ${p.last4}`;        // last4 exists only here
    case "wallet":
      return `${p.provider} (${p.phone})`;       // provider and phone only here
  }
}
```

`method` is the **discriminant**: checking it tells TypeScript which variant you have, so you can only use fields that exist in that variant.

## 9.2 The `Result` pattern: a delivery receipt

!!! analogy "Analogy: a courier's receipt"
    When a courier attempts a delivery, the receipt says either "✓ Delivered: here's your parcel" or "✗ Failed: here's why". Never both, never neither.

```ts
type Result<T, E> =
  | { ok: true; value: T }
  | { ok: false; error: E };

function divide(a: number, b: number): Result<number, "DIVIDE_BY_ZERO"> {
  if (b === 0) {
    return { ok: false, error: "DIVIDE_BY_ZERO" };
  }
  return { ok: true, value: a / b };
}

const r = divide(10, 2);
if (r.ok) {
  console.log(r.value);    // TypeScript knows value exists here
} else {
  console.log(r.error);    // ...and error exists here
}
```

It's just a discriminated union with `ok` as the tag.

**Why not just `throw`?** A thrown error is invisible in the function's type: nothing reminds the caller to handle it. A `Result` puts failure in the type, so callers **must** check `ok` before they can touch `value`. Use `Result` for expected failures (slot taken, invalid input) and `throw` for unexpected ones (bugs, the database is down). Chapter 12 covers throwing.

## 9.3 Exhaustive checks with `never`: a checklist the compiler enforces

```ts
type Light = "red" | "yellow" | "green";

function action(light: Light): string {
  switch (light) {
    case "red":
      return "stop";
    case "yellow":
      return "slow down";
    case "green":
      return "go";
    default: {
      const unreachable: never = light;   // "this line should be impossible"
      throw new Error(`Unknown light: ${unreachable}`);
    }
  }
}
```

How it works:

1. `never` is the type of **a value that can't exist**.
2. After the three cases, TypeScript knows every possible `light` has been handled. Nothing is left over, so assigning `light` to a `never` is fine.
3. Now someone adds `"blue"` to `Light` and forgets a `case`. At the `default` line, `light` could be `"blue"`, and `"blue"` can't go into `never`, so you get a **compile error** pointing at the switch you forgot.

In a real codebase, a new error type or status gets added months later, and the compiler finds every `switch` that needs updating.

## 9.4 Generics: a label with a blank

!!! analogy "Analogy: a storage box label"
    Picture a label that says "Box of ______". You fill in the blank when you use it: "Box of shoes", "Box of books". A generic type parameter, written `<T>`, is that blank.

```ts
function firstItem<T>(list: T[]): T | undefined {
  return list[0];
}

firstItem(["a", "b"]);   // T is string → returns string | undefined
firstItem([1, 2]);       // T is number → returns number | undefined
```

You write the function **once**, and it works for any type while staying type-safe. TypeScript fills in `T` from what you pass in.

Generic types work the same way:

```ts
type Box<T> = { label: string; content: T };
const shoes: Box<string[]> = { label: "Shoes", content: ["sneakers", "sandals"] };
```

`Result<T, E>` from section 9.2 has two blanks: what you get on success (`T`) and what you get on failure (`E`).

### Constraints: "any type, as long as..."

Sometimes the blank can't be *anything*. `extends` adds a requirement:

```ts
// T can be any type, as long as it has an id
function findById<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}

findById(services, "svc_1");   // returns Service | undefined
findById(staff, "st_4");       // returns Staff | undefined
```

## 9.5 Utility types: new types from existing ones

TypeScript has built-in generic types that transform other types. These map perfectly onto REST APIs:

```ts
type Book = { id: string; title: string; author: string; year: number; createdAt: string };

type CreateBookInput = Omit<Book, "id" | "createdAt">;  // the client doesn't send these
type UpdateBookInput = Partial<CreateBookInput>;         // PATCH: every field optional
type BookSummary     = Pick<Book, "id" | "title">;       // only these fields
type StockById       = Record<string, number>;           // { [bookId: string]: number }
type FrozenBook      = Readonly<Book>;                   // nothing can be reassigned
```

| Utility | Meaning | Typical use |
|---|---|---|
| `Omit<T, K>` | `T` without fields `K` | Create inputs (no `id`, no `createdAt`) |
| `Partial<T>` | Every field optional | `PATCH` bodies |
| `Pick<T, K>` | Only fields `K` | Summaries, list views |
| `Record<K, V>` | An object with keys `K` and values `V` | Lookups, counts |
| `Readonly<T>` | Every field `readonly` | Values that must not change |

!!! mistake "`Partial<Book>` for updates"
    `type UpdateBookInput = Partial<Book>` lets a client "update" the `id` or `createdAt`. In Slotify, `Partial<Service>` would even let someone change `businessId`, moving a service into someone else's business. Base updates on the **create input**: `Partial<CreateBookInput>`.

## 9.6 `unknown` and type guards: a parcel from a stranger

!!! analogy "Analogy"
    You don't rip open a parcel from a stranger and start using what's inside. You check it first. Data from the outside world (request bodies, files, environment variables) is that parcel.

TypeScript has two "could be anything" types:

```ts
const a: any = JSON.parse(text);
a.whatever.you.want();     // compiles, then crashes at runtime. any switches checking OFF.

const u: unknown = JSON.parse(text);
u.name;                    // ✗ error: 'u' is of type 'unknown'. You must check first.
```

!!! idea "Rule"
    **Never use `any`. Use `unknown` for outside data**, then narrow it with checks. `unknown` is the honest type: "I don't know what this is yet."

### Checking an `unknown` step by step

```ts
type User = { name: string; age: number };

function parseUser(input: unknown): Result<User, string> {
  // Check 1: is it an object at all? (typeof null is "object", so exclude null)
  if (typeof input !== "object" || input === null) {
    return { ok: false, error: "body must be an object" };
  }
  // Check 2: does it have a non-empty string name?
  if (!("name" in input) || typeof input.name !== "string" || input.name.trim() === "") {
    return { ok: false, error: "name must be a non-empty string" };
  }
  // Check 3: does it have a whole-number age, 0 or more?
  if (!("age" in input) || typeof input.age !== "number" || !Number.isInteger(input.age) || input.age < 0) {
    return { ok: false, error: "age must be a whole number, 0 or more" };
  }
  // Every check passed: TypeScript now knows the types
  return { ok: true, value: { name: input.name, age: input.age } };
}

parseUser(JSON.parse('{"name":"Ali","age":25}'));    // { ok: true, value: {...} }
parseUser(JSON.parse('{"name":"Ali","age":"25"}'));  // { ok: false, error: "age must be..." }
parseUser(JSON.parse("[1,2]"));                      // { ok: false, error: "name must be..." }
```

Notice how much code this takes for just two fields. That's exactly the problem the Zod library solves in Chapter 15. Writing it by hand once means you'll understand what Zod does for you.

### Type guards: reusable checks

A function whose return type is `value is SomeType` is a **type guard**. When it returns `true`, TypeScript treats the value as that type:

```ts
const ROLES = ["owner", "staff", "customer"] as const;
type Role = (typeof ROLES)[number];   // "owner" | "staff" | "customer"

function isRole(value: unknown): value is Role {
  return ROLES.some((role) => role === value);
}

const input: unknown = "staff";
if (isRole(input)) {
  const role: Role = input;   // ✓ narrowed
}
```

Two new tricks here:

- `as const` tells TypeScript the array will never change, so its type is the exact values, not just `string[]`.
- `(typeof ROLES)[number]` means "the type of any element of `ROLES`". So the union is generated from the list, and you never have to keep two lists in sync.

!!! warning "`as` is a promise, not a check"
    `const user = data as User` doesn't check anything. It just tells TypeScript "trust me". If you're wrong, the program crashes later, far from the real cause. Avoid `as` (and the `!` non-null operator) unless you have a very good reason.
