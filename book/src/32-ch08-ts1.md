JavaScript lets you write `booking.startTime.toUpperCase()` even when `startTime` is a date, and you only find out when it crashes in production. TypeScript finds that mistake while you type. This chapter covers the everyday core: the types you'll write in every file.

!!! learn "What you'll learn"
    - What TypeScript is (and what it isn't)
    - Setting up a strict TypeScript project
    - Basic types and type inference
    - Object types, optional and readonly fields
    - Function types
    - Union types and narrowing

## 8.1 What TypeScript really is

TypeScript = JavaScript + **types**. You add notes like "this is a number" or "a Booking always has these fields", and the TypeScript compiler (`tsc`) checks that your code respects them.

!!! analogy "Analogy: a spell-checker for logic"
    A spell-checker underlines words that don't exist before you send the email. TypeScript underlines code that can't work (a missing field, a typo in a status, a string where a number belongs) before you run it.

**Types are erased at runtime.** TypeScript checks your code and then disappears. When your program runs, it's plain JavaScript. That leads to the most important fact in Phase 3:

!!! idea "TypeScript can't check data from the outside world"
    When JSON arrives from a client, TypeScript has no idea what's inside, because the check happened earlier, while you were writing code. That's why backends must **validate** incoming data at runtime. You'll do that by hand in Chapter 9 and with the Zod library in Chapter 15.

## 8.2 Setting up a project

Node 24 can run `.ts` files directly: it strips the types out and runs the JavaScript. But it **doesn't check** the types. Checking is the job of `tsc`. So your workflow is:

```bash
node src/index.ts      # run it
npx tsc --noEmit       # check it: report errors, output nothing
```

Set up the `ch08/` project like this:

```bash
mkdir ch08 && cd ch08
npm init -y
npm install -D typescript @types/node
npm pkg set type=module scripts.check="tsc --noEmit"
mkdir src
```

Then create `tsconfig.json`:

```json
{
  "compilerOptions": {
    "target": "esnext",
    "module": "nodenext",
    "strict": true,
    "noEmit": true,
    "allowImportingTsExtensions": true,
    "verbatimModuleSyntax": true,
    "erasableSyntaxOnly": true,
    "noUncheckedIndexedAccess": true,
    "skipLibCheck": true,
    "types": ["node"]
  },
  "include": ["src"]
}
```

What each setting does:

| Setting | Meaning |
|---|---|
| `target: esnext` | Use the newest JavaScript features (Node 24 supports them) |
| `module: nodenext` | Follow Node's modern module rules |
| `strict: true` | Turn on all the strict checks. The two most important: `strictNullChecks` (`null` and `undefined` aren't allowed just anywhere) and `noImplicitAny` (no accidental untyped values) |
| `noEmit: true` | Only check; don't write JavaScript files (Node runs the `.ts` files directly) |
| `allowImportingTsExtensions` | Allow `import ... from "./types.ts"` with the `.ts` ending, which Node needs |
| `verbatimModuleSyntax` | Forces `import type` for type-only imports (section 8.8 explains why) |
| `erasableSyntaxOnly` | Forbids TypeScript features Node can't simply strip out, like `enum` |
| `noUncheckedIndexedAccess` | Reading `arr[i]` or `obj[key]` gives `T \| undefined`, because the slot might be empty |
| `skipLibCheck` | Don't type-check library files in `node_modules` (faster) |
| `types: ["node"]` | Include Node's types (`process`, `Buffer`, `node:fs`...) |

!!! note "Using your Lesson 02 folder"
    If you already set up `02-typescript/` in Lesson 02, you can keep working there instead of `ch08/`. It has the same configuration.

## 8.3 Basic types and inference

```ts
let businessName: string = "Glow Salon";
let priceCents: number = 150000;
let isOpen: boolean = true;

const tags: string[] = ["hair", "beard"];          // array of strings
const openingHours: [number, number] = [9, 18];    // tuple: exactly two numbers
```

You often don't need to write the type at all. TypeScript **infers** it from the value:

```ts
let city = "Lahore";   // TypeScript knows city is a string
city = 42;             // ✗ Type 'number' is not assignable to type 'string'.
```

!!! idea "Rule of thumb"
    **Write types for function parameters and return values. Let TypeScript infer the types of local variables.**

### Choosing the right type for real data

| Data | Type | Why |
|---|---|---|
| Price | `number`, in **cents** | Decimals cause rounding errors (Chapter 7) |
| Phone number | **`string`** | `03001234567` would lose its leading zero as a number, and `+92` can't be stored. **If you never do maths on it, it's a string.** (Same for CNIC numbers and postal codes.) |
| Time zone | `string`, like `"Asia/Karachi"` | It's a name, not a date |
| ID | `string` | UUIDs like `"b3f1c2..."` are strings. Pick one ID type and use it **everywhere**. |
| Status | a union like `"pending" \| "confirmed"` | Only valid values are allowed (section 8.6) |

## 8.4 Object types

Describe the shape of an object with `type`:

```ts
type Service = {
  readonly id: string;       // can't be changed after creation
  name: string;
  durationMinutes: number;
  priceCents: number;
  description?: string;      // optional: string | undefined
};

const haircut: Service = {
  id: "svc_1",
  name: "Haircut",
  durationMinutes: 30,
  priceCents: 150000,
};

haircut.name = "Men's haircut";   // ✓
haircut.id = "svc_2";             // ✗ Cannot assign to 'id' because it is a read-only property.
```

Optional fields might be `undefined`, so TypeScript makes you handle that:

```ts
haircut.description.toUpperCase();                    // ✗ 'haircut.description' is possibly 'undefined'.
haircut.description?.toUpperCase() ?? "(none)";       // ✓
```

!!! note "`type` or `interface`?"
    You'll also see `interface Service { ... }`. For object shapes they're almost identical. This book uses `type` everywhere, because `type` can also describe unions, and `interface` can't. Pick one style and be consistent.

## 8.5 Functions

```ts
function totalPrice(services: Service[], discountPercent = 0): number {
  const sum = services.reduce((acc, s) => acc + s.priceCents, 0);
  return Math.round(sum * (1 - discountPercent / 100));
}

const double = (n: number): number => n * 2;

function logMessage(message: string): void {   // void: returns nothing useful
  console.log(`[log] ${message}`);
}

function greet(name?: string): string {        // optional parameter
  if (name) {
    return `Hello, ${name}!`;
  }
  return "Hello, stranger!";
}
```

!!! mistake "Functions should return values, not print them"
    A function like `durationLabel(90)` should **return** `"1 h 30 min"`. Printing is the caller's decision. Functions that return values can be reused, combined and tested; functions that print can't.

## 8.6 Union and literal types: the dropdown menu

A **union** type means "one of these". A **literal** type is a single exact value. Together, they work like a dropdown menu:

```ts
type BookingStatus = "pending" | "confirmed" | "cancelled" | "completed";
type Currency = "PKR" | "USD" | "AED";

let status: BookingStatus = "confirmed";   // ✓
status = "canceled";                       // ✗ typo caught!
```

The real error message is even helpful:

```output
error TS2820: Type '"canceled"' is not assignable to type 'BookingStatus'. Did you mean '"cancelled"'?
```

!!! analogy "Analogy: a dropdown on a form"
    A "Status" dropdown on a website only lets you pick from the list. You can't type "maybe". A string union does the same thing in code.

!!! mistake "Don't model a status as a number or an object"
    `status: number` → what does `3` mean? Nobody knows. `status: { status: number }` → you end up writing `booking.status.status`. A union of readable strings is clear, safe and self-documenting.

Unions aren't only for strings: `string | number`, `Service | undefined` and `Date | null` are all common.

## 8.7 Narrowing: TypeScript follows your `if`s

When a value could be several types, you must check which one it is before using type-specific features. TypeScript follows your checks and **narrows** the type inside each branch:

```ts
function formatId(id: string | number): string {
  if (typeof id === "number") {
    return id.toString().padStart(6, "0");   // in here, id is a number
  }
  return id.toUpperCase();                   // in here, id must be a string
}

formatId(42);      // "000042"
formatId("abc");   // "ABC"
```

The checks TypeScript understands:

| Check | Example | Narrows... |
|---|---|---|
| `typeof` | `typeof x === "string"` | primitives: string, number, boolean... |
| Equality | `x === undefined`, `status === "confirmed"` | to that exact value |
| Truthiness | `if (name) { ... }` | removes `undefined`, `null`, `""`, `0` |
| `in` | `if ("phone" in person)` | objects that have that property |
| `Array.isArray` | `Array.isArray(x)` | to an array |

```ts
type Customer = { name: string; phone: string };
type Staff = { name: string; serviceIds: string[] };

function describePerson(p: Customer | Staff): string {
  if ("phone" in p) {
    return `Customer ${p.name}, phone ${p.phone}`;
  }
  return `Staff ${p.name}, does ${p.serviceIds.length} services`;
}
```

### Narrowing array access

With `noUncheckedIndexedAccess`, reading by index gives `T | undefined`, because the index might be past the end:

```ts
const tags = ["hair", "beard"];
const first = tags[0];          // string | undefined
first.toUpperCase();            // ✗ 'first' is possibly 'undefined'.

if (first !== undefined) {
  first.toUpperCase();          // ✓ narrowed to string
}
```

This setting catches the exact bug from Chapter 3's error detective (`list[i + 1]` going past the end).

## 8.8 Modules: `export`, `import` and `import type`

Split code into files. Each file is a **module**:

```ts
// src/types.ts
export type Currency = "PKR" | "USD" | "AED";
export type Service = { id: string; name: string; priceCents: number; currency: Currency };
```

```ts
// src/format.ts
import type { Currency } from "./types.ts";

export function formatPrice(cents: number, currency: Currency): string {
  // ...
}
```

```ts
// src/index.ts
import { formatPrice } from "./format.ts";
console.log(formatPrice(150000, "PKR"));
```

- Use **`import type`** when you import only types. Types don't exist at runtime, so Node must remove these imports completely. (`verbatimModuleSyntax` makes `tsc` remind you.)
- Write the **`.ts` extension** in local imports when Node runs your files directly.

!!! warning "A file without `export` or `import` is a \"script\""
    If a file has no `import` or `export` at all, TypeScript treats it as an old-style script, and everything in it becomes **global**: visible in every other file. That causes strange "duplicate identifier" errors. Always `export` what other files need.

## 8.9 Reading compiler errors

Here are real errors from `npm run check`, and how to read them:

```output
src/broken.ts(6,7): error TS2741: Property 'priceCents' is missing in type '{ id: string; name: string; }' but required in type 'Service'.
```

- `src/broken.ts(6,7)`: file, **line 6, column 7**. VS Code jumps there if you <kbd>Ctrl</kbd>+click.
- `TS2741`: the error code. Search for it if the message isn't clear.
- The message: the object you wrote has `id` and `name`, but `Service` also requires `priceCents`.

| Message (shortened) | Usually means |
|---|---|
| `Type 'X' is not assignable to type 'Y'` | You put the wrong kind of value somewhere |
| `Property 'p' is missing in type ... but required in type 'T'` | You forgot a required field |
| `Object literal may only specify known properties, and 'colour' does not exist` | Extra field, often a typo (`colour` vs `color`) |
| `'x' is possibly 'undefined'` | You must check for `undefined` first (narrowing) |
| `Argument of type 'string' is not assignable to parameter of type 'number'` | You passed the wrong type to a function |

When an error is long, read the **last line** first: that's usually the most specific part.
